# Phase 2 Implementation Plan — Public Site & Data Product

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the index as a public **data product**: one canonical daily artifact, published as versioned JSON/CSV from a git-vintaged public data repo behind a CDN, with a thin static site rendering it. No backend, no database, no accounts.

**Architecture:**

```
daily cron (GitHub Actions)
  incremental ingest (top-up since last snapshot)      [Task 6]
  -> normalize -> universes -> compute                 [exists, Phase 1]
  -> uindex.publish  (build -> self-check -> gate)     [Tasks 2-4]
  -> commit artifacts to public data repo (vintage)    [Task 5]
  -> deploy static site to CDN                         [Tasks 8-9]
```

**Tech stack:** Python 3.11+ (publish, checks), `jsonschema` for contract validation, plain HTML/CSS/vanilla JS for the site (no framework, no bundler), GitHub Actions for CI, GitHub Pages or Cloudflare Pages for hosting.

**Working directory:** everything here is relative to `uncertainty-index/` inside `/Users/kianjagtiani/Documents/pred_market_baskets`, except the data repo and site repo, which are separate repositories (Task 5, Task 9).

## Global Constraints

- Spec: `docs/specs/2026-07-29-phase2-site-design.md` governs, **except** where this plan records an explicit conflict (see "Conflicts with the spec" below) — those resolutions win, because they postdate the spec.
- **Name/domain are TBD.** Every artifact, repo, and page in this plan uses placeholders: `<DATA_REPO>`, `<SITE_REPO>`, `<CDN_BASE>`, `<SITE_NAME>`. A naming pass happens before launch (Task 11). Nothing below may hardcode a name outside `src/uindex/publish/config.py` and one site config file.
- **Launch gate stands:** no public launch on a number that failed its own validation. Tasks 1–10 may be built and dry-run at any time; Task 11 (public DNS + announcement) is gated on a passing validation report.
- All Phase 2 tunables live in `src/uindex/publish/config.py`, never hardcoded in logic modules — same rule as `uindex.config`.
- Tests never touch the network. Publish tests run against committed fixture parquets; site CI builds against fixture JSON.
- Every publish is atomic: build to a temp dir, validate, then swap/commit. **No partial publishes, ever.** A failed check produces zero commits and zero deploys.
- Published history is append-only unless a revision is explicitly declared (Task 4/5). Silent restatement is a build failure, not a warning.
- Honest disclosure is a hard requirement, not a nicety: any staleness, carry-forward, or coverage gap that affects a published number must be machine-readable in the artifact **and** visible on the page rendering it.
- Commit after every task; message style matches `git log` (`feat:`/`fix:`/`docs:`/`test:`).

## Decisions from the 2026-08-01 work that this plan is built on

These postdate the spec and are binding:

1. **Polymarket PIT volume comes from a frozen source.** The Goldsky
   `orderbook-subgraph/0.0.1` sweep has a hard coverage horizon at
   **2026-04-28** (docs/research/negrisk-coverage-probe.md §2, §5). The sweep
   records a coverage manifest with `max_fill_timestamp`; days beyond the
   horizon are **NaN, never 0**, and rolling weights carry forward causally
   from the last covered day, flagged. Phase 2 must surface that flag and
   horizon in every artifact and on every page. Residual negRisk gaps
   (pm_559700-class, 0% coverage) are a second, separate disclosure.
2. **Gamma's keyset endpoint only serves market ids ≥ 559651.** Older
   metadata comes from the separate legacy id-batch sweep. **Daily
   incremental updates need only the keyset path; any full-history metadata
   refetch must run both sweeps.** A refetch that runs only keyset silently
   loses the entire 2024-01-01 → 2025-07-03 catalog, including the 2024
   election markets the validation depends on.
3. **A source change forbids cursor resume.** Established when switching
   subgraphs (probe §5: "do not attempt to resume the old resync cursor
   against the new subgraph; start over"). Generalized in Task 7 into the
   source-fingerprint rule.

## Conflicts with the spec (resolved here; these resolutions win)

| # | Spec says | Reality | Resolution |
|---|---|---|---|
| C1 | `publish` reads `indices.parquet` + `constituents.parquet` and emits per-index constituent contributions | `constituents.parquet` holds only `date, index, gauge, n_constituents` — **counts, not membership**. Per-market weights/values exist only in the in-memory flagged panel, which `pipeline.main()` never persists. | Task 1 extends the pipeline to persist a membership frame. `publish` reads three inputs, not two. |
| C2 | Constituent rows "linking out to the venue" | Neither venue link key survives into the artifacts: PM `slug` is never ingested (`markets_to_df` drops it), and Kalshi `ticker`/`series_ticker` are dropped by `normalize.META_COLS`. | Task 1 adds `slug` to PM ingestion and carries link keys through normalize. Adding a column to PM metadata is a source-schema change and therefore triggers the Task 7 full-history refetch (**both** sweeps, per decision 2). |
| C3 | Incremental ingest = "crawl markets with activity since the stored snapshot" | No activity-ordered endpoint exists on either venue. Gamma keyset is **id-ordered** and floored at 559651; Kalshi paginates by cursor. "Activity since snapshot" is not directly expressible. | Task 6 replaces it with: id-ordered keyset top-up (catches new listings) **plus** a targeted id-batch refresh of a known id set (constituents + trailing-30-day closers). Same effect, achievable with the endpoints that exist. |
| C4 | Failure behavior = serve the last good day with an "as of" stamp | One staleness axis is insufficient. With the volume horizon frozen at 2026-04-28, `as_of` can be *today* while the weights behind the number are months old. | Two independent axes (Task 3): **index freshness** (last published day — hard gate, blocks publish) and **input coverage** (per-stream horizons — disclosed, never blocking). |
| C5 | "Git history = point-in-time vintages for free" | Free vintages are not free *revision semantics*. Nothing in the spec says what happens when a previously published day's value changes. | Task 4 adds a restatement detector and Task 5 defines revision commits, tags, and `REVISIONS.md`. Undeclared restatement fails the build. |
| C6 | Failure notice via GitHub Actions only | A silently-succeeding job that publishes a stale or wrong artifact is the more likely failure, and Actions notifies on neither. | Task 10 adds an external liveness probe and soft-anomaly reporting independent of the job's own exit code. |

### Task 3: JSON/CSV API contract, versioned

The CDN-served files *are* the public API. They get a written, machine-checkable, versioned contract.

**Files:**
- Create: `src/uindex/publish/schema/v1/latest.schema.json`, `constituents.schema.json`, `coverage.schema.json`, `manifest.schema.json`, `methodology.schema.json`
- Create: `tests/golden/v1/` (golden artifact set built from the Task 2 fixtures)
- Test: `tests/test_publish_contract.py`
- Create: `docs/api-v1.md` (human-readable contract, source for the /data page)

**Contract rules:**
- Every JSON document carries `"schema_version": "1.x"` at the top level. Paths are version-prefixed: `<CDN_BASE>/v1/...`.
- **Additive** changes (new optional field) bump the minor version and keep the same path. **Breaking** changes (removing/renaming a field, changing a type or units, changing the meaning of a value) mint `/v2/` and `/v1/` continues to be published for **≥ 180 days** after the `/v2/` launch. Deprecations are announced in `/v1/meta/deprecations.json` with a `sunset_date` before, not after, the fact.
- CSV series files: header `date,index,gauge,raw,value,n_constituents,flags`; ISO dates; empty string for null; `flags` is a `|`-separated set drawn from a closed vocabulary (`weights_carried_forward`, `seed_period`, `partial_coverage`).
- The **coverage block** is part of the contract, not decoration. `meta/coverage.json` and the `coverage` object inside `latest.json`:
  - `index_last_date`, `as_of`, `built_at`
  - `streams: {<stream_id>: {source, horizon, stale_days, status}}` where `status ∈ {current, stale, frozen}` and `stream_id ∈ {polymarket.markets, polymarket.prices, polymarket.volume, kalshi.markets, kalshi.prices}`
  - `weights_carried_forward: bool`, `carry_forward_since: date|null`, `carried_weight_share: float` — the share of today's GLOBAL weight coming from carried-forward (post-horizon) values. This is the number that tells a reader how much of today's index rests on stale weights; it is mandatory, not optional.
  - `known_gaps: [{scope, description, doc_url}]` — carries the residual negRisk 0%-coverage disclosure.
- The `flags` vocabulary and `status` enum are closed sets pinned in the schema; adding a value is an additive change, removing one is breaking.

- [ ] **Step 1:** Write the JSON Schemas.
- [ ] **Step 2:** Write `tests/test_publish_contract.py`: validate every Task 2 fixture output against its schema; assert the golden files match byte-for-byte.
- [ ] **Step 3:** Write `docs/api-v1.md` with every field, its type, units, null semantics, and an example request per endpoint.
- [ ] **Step 4:** Commit.

**Acceptance criteria:**
- Every artifact validates against its schema in CI; an intentionally corrupted fixture fails validation (negative test present).
- The golden-file test fails if any field is added, removed, renamed, or reordered — so a contract change cannot land without a deliberate golden update in the same commit.
- `docs/api-v1.md` documents every field present in the golden files, verified by a test that diffs the schema's property set against the doc's field list.
- The coverage block's `carried_weight_share` is present and non-null in the golden `latest.json`.

### Task 4: Publish gate — self-checks, staleness policy, restatement detection

`build` produces; this decides whether the world sees it. Closes conflicts C4 and C5.

**Files:**
- Create: `src/uindex/publish/checks.py`, `src/uindex/publish/cli.py`
- Test: `tests/test_publish_checks.py`

**Interfaces:**
- `checks.run(candidate_dir: Path, previous_dir: Path | None, opts: PublishOpts) -> CheckReport` — pure comparison of two artifact sets. `previous_dir` is the last published vintage, fetched from the data repo.
- `CheckReport` separates **hard** failures (publish aborts, exit nonzero, zero commits) from **soft** anomalies (publish proceeds; anomalies are written into `meta/manifest.json` and surfaced by monitoring).
- CLI: `python -m uindex.publish [--as-of DATE] [--dry-run] [--revision "reason"]`.

**Hard checks (any failure = no publish):**
1. Schema validation of every artifact (Task 3).
2. All 8 indices × 2 gauges present; no index missing without a declared reason.
3. `index_last_date` is within `PUBLISH_MAX_INDEX_LAG_DAYS` (default 3) of `as_of` — **index freshness gate**.
4. Every non-null `value ∈ [0, 100]`; every `raw` finite; `n_constituents ≥ MIN_CONSTITUENTS` (default 5) for every published day of every index.
5. Series dates strictly increasing, no duplicates, no future dates.
6. `Σ contribution == raw` within 1e-9 for every published (index, gauge) day.
7. **Restatement detector.** For every date present in both the candidate and the previous vintage, `|candidate.value − previous.value| ≤ RESTATEMENT_EPS` (default 1e-6) and `|Δraw| ≤ RESTATEMENT_EPS`. Any violation aborts the publish **unless** `--revision "reason"` was passed. Rationale: `compute.percentile_scale` is an expanding window over strictly-prior history, so a new day cannot change a past day's value by construction — therefore any change to a past value is, by definition, an upstream data revision, and must be declared and recorded (Task 5), never absorbed silently.
8. Previously published dates are never *dropped* from the series (same rule, deletion case).
9. **Source reconciliation gate** (the blocking half of Task 7b). Reads the reconciliation report the daily ingest writes to `data/raw/reconciliation.json`: `{checked_at, armed: bool, results: [{stream, market_id, stored, observed, deviation}]}`. Rules:
   - Any `deviation > RECONCILE_TOL` (default 1%) → **hard fail**, naming the offending stream and market. Upstream has revised history (Task 7b); the stream is scheduled for a full-history refetch and the next publish is a revision with cause `upstream_reindex`.
   - Report present and `armed: false`, or report absent → **not a pass and not a fail**: publish proceeds but `manifest.checks.reconciliation = "not_armed"` is recorded and the Task 10 monitor alerts on it. This is deliberate: Task 4 lands before Task 7, and a gate that silently returns "pass" when its input does not yet exist is indistinguishable from a working gate — the failure mode that makes safety checks worthless. The disarmed state must be *visible*, never absorbed.
   - Report older than 48 h → treated as absent (a stale reconciliation proves nothing about today's source).

   Task 4 implements the gate and the `not_armed` path against a fixture report. Task 7 arms it by writing the real report; it does not re-implement the gate.

**Not a hard check — disclosed instead (the C4 second axis):**
- Volume/input staleness never blocks publication. A frozen volume horizon degrades *weights*, not the index's existence, and blocking would mean publishing nothing at all from 2026-04-28 onward. It sets `coverage.streams[...].status = frozen`, `weights_carried_forward = true`, and populates `carried_weight_share`. The site's disclosure banner (Task 9) is the mitigation.

**Soft anomalies (recorded, non-blocking):**
- GLOBAL day-over-day |Δvalue| > 40 points.
- Membership churn vs previous vintage > 20% for any index.
- `n_constituents` drop > 30% day-over-day.
- `carried_weight_share` crossing above 0.5.

- [ ] **Step 1:** Write failing tests, one per hard check, each with a candidate/previous pair engineered to trip exactly that check and nothing else.
- [ ] **Step 2:** Write the restatement test explicitly both ways: undeclared restatement aborts; the same restatement with `--revision` passes and lands a revision record.
- [ ] **Step 3:** Write the reconciliation-gate tests against fixture reports: in-tolerance passes, out-of-tolerance hard-fails, absent/`armed: false`/stale-report all yield `not_armed` (publish proceeds, manifest records it, exit code unaffected).
- [ ] **Step 4:** Implement `checks.py` and `cli.py`.
- [ ] **Step 5:** Commit.

**Acceptance criteria:**
- Each hard check has a test that fails the publish and a test that passes it — no check is only ever exercised in the passing direction.
- The reconciliation gate's three states (pass / hard fail / `not_armed`) are each covered, and `not_armed` is asserted to appear in `meta/manifest.json` — a disarmed gate can never look like a passing one.
- `--dry-run` produces a full `CheckReport` and writes nothing outside the temp dir.
- A hard failure leaves the data repo working tree untouched (asserted, not assumed).
- Soft anomalies appear in `meta/manifest.json` with enough detail to act on (which index, which magnitude), and do not affect the exit code.

### Task 5: Data repo layout, vintages, and revision semantics

The public data repo `<DATA_REPO>` is a separate repository from the compute code and the site — all three version independently (per spec).

**Files (in `<DATA_REPO>`):**
- `v1/latest.json`, `v1/series/<INDEX>.csv`, `v1/constituents/<INDEX>.json`, `v1/meta/*.json`
- `REVISIONS.md` — human-readable revision log
- `revisions.json` — the same, machine-readable, served from the CDN
- `README.md` — what this repo is, licensing, citation block, "do not open PRs against generated files"
- `LICENSE` — data license (CC BY 4.0 proposed; confirm at Task 11)

**Vintage semantics:**
- One commit per successful publish: `data: YYYY-MM-DD` (message style matches the compute repo).
- Each publish commit is tagged `v1/YYYY-MM-DD`. A vintage is retrieved by tag:
  `https://raw.githubusercontent.com/<owner>/<DATA_REPO>/v1/2026-08-01/v1/latest.json`. This retrieval form is documented on the /data page and in `docs/api-v1.md`.
- `meta/manifest.json` in every commit records build provenance: compute-repo git SHA, `uindex` version, per-stream source fingerprints (Task 7), row counts, per-artifact SHA-256, soft anomalies, and `revision` (integer, 1 for a normal publish).
- **History is never rewritten.** No force-push, ever. Branch protection on the data repo's default branch forbids force-push and deletion.

**Revision semantics (the C5 resolution):**
- A *revision* is any publish that changes or removes a previously published value. It is only possible via `--revision "reason"`, which:
  1. commits as `data: revise YYYY-MM-DD..YYYY-MM-DD — <reason>`,
  2. tags `v1/<as_of>-r<N>` with N incremented from the prior revision that day,
  3. bumps `manifest.revision`,
  4. prepends an entry to `REVISIONS.md` and `revisions.json`: `{date_published, affected_range, cause, streams_refetched, max_abs_value_change, prior_vintage_tag}`.
- The prior vintage remains permanently reachable at its tag. A consumer can always diff two vintages to see exactly what was restated.
- Revision causes are drawn from a closed vocabulary matching Task 7's invalidation triggers: `no_data_invalidated`, `source_fingerprint_change`, `upstream_reindex`, `metadata_refresh`, `methodology_change`, `defect_fix`.
- **Methodology changes are not revisions.** A change to index math mints a new schema major (`/v2/`) and republishes full history under it; `/v1/` continues unchanged for its deprecation window. Restating history under the same version number because the method changed is exactly the credibility failure that sinks published indices.

- [ ] **Step 1:** Create `<DATA_REPO>` (private initially; public at Task 11), with README, LICENSE, and the empty `v1/` tree.
- [ ] **Step 2:** Enable branch protection: no force-push, no branch deletion, linear history.
- [ ] **Step 3:** Implement `src/uindex/publish/repo.py` — clone/pull, stage, commit, tag, push; all git operations idempotent and safe to re-run after a partial failure.
- [ ] **Step 4:** Test with a local bare repo fixture (no network): normal publish, revision publish, and a re-run after a simulated mid-push crash.
- [ ] **Step 5:** Commit.

**Acceptance criteria:**
- Two consecutive publishes of identical artifacts produce **no** commit (nothing changed) rather than an empty commit or a spurious revision.
- A revision publish produces exactly one commit, one tag, and one `REVISIONS.md` entry; the prior tag still resolves to the prior content.
- A publish interrupted between commit and push, then re-run, converges to one commit and one tag — no duplicates, no orphan tags.
- Force-push is rejected by the remote (verified once, manually, against the real repo).

### Task 6: Incremental update pipeline

Top-up mode for both venues so the daily job does bounded work. Closes conflict C3.

**Files:**
- Modify: `src/uindex/ingest/polymarket.py`, `src/uindex/ingest/kalshi.py`, `src/uindex/ingest/polymarket_volume.py`
- Create: `src/uindex/ingest/refresh.py` — the targeted refresh set and its driver
- Modify: `scripts/run_backfill.sh` → add a `--mode {backfill,daily}` flag, or add `scripts/run_daily.sh` reusing the same portioned/watchdog discipline
- Test: `tests/test_ingest_refresh.py`

**Refresh policy:**

| Cadence | Stream | Action |
|---|---|---|
| Daily | `polymarket.markets` | Keyset top-up from the stored `after_cursor` (**keyset only** — ids ≥ 559651; new listings all fall in this range, so the legacy sweep is not needed daily) |
| Daily | targeted metadata | Id-batch refresh (`/markets?id=…`, ≤ 100 ids/request — the legacy-sweep primitive built by **the overnight plan's** Task 11, reused; not this plan's Task 11) over the **refresh set** |
| Daily | `kalshi.markets` | Cursor top-up + targeted re-fetch of the refresh set's Kalshi tickers |
| Daily | `*.prices` | Full-history fetch for every market in the todo set (prices are fetched whole-history per market, so a re-fetch is exact and idempotent) |
| Daily | `polymarket.volume` | Sweep top-up from the stored `(timestamp, id)` cursor; records the new horizon in the coverage manifest |
| Monthly | all metadata | Full metadata re-crawl: **keyset sweep AND legacy id-batch sweep** (decision 2 — a keyset-only "full" refresh silently drops the pre-2025-07-03 catalog) |

- **Refresh set** = current constituents of any index ∪ markets whose `close_date` falls in the trailing 30 days ∪ markets whose no-data tombstone was invalidated today (Task 7). Their volumes drift and weights depend on them.
- **Todo set for prices** = new markets from the metadata top-up ∪ refresh-set markets whose latest observed price date is older than yesterday ∪ invalidated tombstones.
- **Shared interface with Task 7 — agree on this before either task is implemented.** Task 6 and Task 7 each consume the other's output, so they are coupled and must not be built as independent parallel workstreams (see Dependencies). The coupling resolves into a fixed three-phase order within a single run, defined in Task 7a under "Trigger ordering". The two signatures that pin it:
  - `refresh.refresh_set(constituents, meta, invalidated_early: set[str], today) -> set[str]` — Task 6 owns it; it takes the early-invalidated ids as a plain input and never calls back into the ledger.

#### 7a. The no-data ledger becomes structured and provisional

**The defect:** `no_data_ids.txt` is an append-only flat list with no timestamp and no reason, and `done_ids()` unions it unconditionally. A market tombstoned once is never fetched again. A market that legitimately had no history at first crawl — listed but not yet traded, or crawled before its candles existed — is permanently invisible to the index, and nothing in the system can ever notice.

**The rule:** replace with `no_data.csv`, columns
`market_id, reason, first_marked_utc, last_checked_utc, attempts, source_epoch`,
where `reason ∈ {http_404, empty_history, no_candles}`. Tombstones are classified:

- **Terminal** — never re-checked. Condition: `close_date` is in the past by more than `RESOLUTION_EXCLUSION_DAYS`. **Settlement alone decides terminality; the reason does not narrow it.** A resolved market's history cannot gain rows under *any* of the three reasons — a settled market that returned `no_candles` will never grow candles, exactly as one that returned `http_404` will never start resolving. Restricting terminality to a reason subset would leave every settled `no_candles` market re-checked forever on the backoff schedule, which is the unbounded-cost failure mode this state exists to prevent. `reason` is retained for diagnostics and for the migration audit, not as a classification input.
- **Provisional** — everything else (market still open, or `close_date` unknown). Re-checked when `last_checked_utc` is older than `NO_DATA_RECHECK_DAYS` (default 7), with exponential backoff on `attempts` capped at 30 days, so a permanently dead open-ended market does not cost a fetch a week forever.
- **Terminal is not absolute:** trigger 3 below (source-fingerprint change) wipes the entire ledger for that stream, terminal rows included. Terminality means "no new data can arrive from *this* source," which is exactly the claim a fingerprint change invalidates.

**Immediate invalidation triggers** — drop the tombstone now, fetch on this run:
1. The metadata refresh reports trading activity for a tombstoned market (PM: non-zero `volume24hr`; Kalshi: `volume` increased since the stored value). "No data" is now demonstrably false.
2. The market enters the refresh set (Task 6) — it is a constituent or a recent closer, so its data matters to a published number.
3. The stream's `source_epoch` no longer matches the current fingerprint (7b) — the tombstone was recorded against a different source and carries no information about this one.

**Trigger ordering (this is what makes the Task 6 ↔ Task 7 dependency acyclic).** Triggers 1 and 3 depend only on metadata and fingerprints — never on the refresh set — so a single run evaluates them in a fixed three-phase order:

1. **Phase A** — evaluate triggers 3 then 1. Inputs: source fingerprints, freshly topped-up metadata. Output: `invalidated_early: set[str]`.
2. **Phase B** — `refresh.refresh_set()` is computed, taking `invalidated_early` as one of its three inputs (Task 6).
3. **Phase C** — evaluate trigger 2 against the now-known refresh set, invalidating any tombstones still standing within it. Output: `invalidated_late`. The price todo set is then built from `invalidated_early ∪ invalidated_late ∪` the rest.

Phase C cannot feed back into Phase B: a trigger-2 invalidation adds nothing to the refresh set, because the market was *already in it* — that is what fired the trigger. The apparent cycle is a two-pass computation within one run, not a genuine circular dependency.

**Downstream consequence:** invalidating a tombstone that then yields data *adds rows to past days*, which changes past index values. That is a **revision**, cause `no_data_invalidated`, and it must go through Task 4's `--revision` path. The daily job detects this automatically (the restatement detector fires), so the operator is told rather than the history being quietly rewritten.

#### 7b. Source fingerprints and the full-history refetch rule

**The rule:** `data-overrides/sources.json` records, per stream
(`polymarket.markets`, `polymarket.prices`, `polymarket.volume`,
`kalshi.markets`, `kalshi.prices`):

```
{ "endpoint": "<url or subgraph deployment slug>",
  "entity":   "<graphql entity / API resource>",
  "scaling":  "<named scaling rule id>",
  "schema":   ["<ordered output column list>"],
  "epoch":    <int, bumped by hand for any semantic change> }
```

The **fingerprint** is a hash over those fields. Every store's `manifest.json` records the fingerprint under which its data was collected. At the start of every run, each stream's configured fingerprint is compared with its stored one:

- **Match** → incremental top-up, resume from cursor (Task 6).
- **Mismatch** → **full-history refetch of that stream, mandatory**: delete cursor state, part-files, the finalized parquet, **and the stream's no-data ledger**; restart from `BACKFILL_START`. Resuming a cursor across a source change is forbidden — the cursor's coordinates do not mean the same thing on the new source (probe §5). For `polymarket.markets`, a full refetch runs **both** the keyset and legacy sweeps (decision 2).
- The refetch's recomputed history is published as a revision, cause `source_fingerprint_change`.

Fingerprint changes this plan already knows about: Task 1's PM `slug` column (schema change) and, if it ever lands, the on-chain RPC volume source.

**Silent upstream revision detection.** A subgraph can re-index and change historical answers with no fingerprint change at all — the probe already documented two subgraphs disagreeing about the same historical market (§3, Weinstein: 423 vs 7,595 fills). Guard: `data-overrides/reconcile_sample.csv` pins ~20 settled markets spanning both venues, both eras, negRisk and not, all fully resolved before the current horizon so their true totals are frozen. The daily job re-queries each and compares to the stored total:

- Deviation ≤ `RECONCILE_TOL` (default 1%) for all samples → normal publish.
- Any deviation > tol → upstream has revised history. **Publish is blocked**, the stream is scheduled for a full-history refetch, and the operator is notified. The next publish after the refetch is a revision with cause `upstream_reindex`.
- Sample rows are never used to *correct* data — only to detect that the source moved. Using them as a correction factor would smuggle a fudge into the index.

**Where the blocking actually happens.** The probe here only *writes evidence*; it never calls into the publish path. The daily ingest writes `data/raw/reconciliation.json` (`{checked_at, armed: true, results: [...]}`), and **Task 4's hard check 9** reads it and decides. Splitting it this way keeps `checks.run()` a pure comparison of files on disk — no network, no ingest imports — which is what lets the whole gate be tested offline. Task 7 must not add a second, independent blocking path.

- [ ] **Step 1:** Write failing tests: terminal vs provisional classification **across all three reasons** (a settled `no_candles` market must be terminal); backoff schedule; each of the three immediate triggers; the A→B→C phase ordering (trigger 2 firing does not re-expand the refresh set); fingerprint match/mismatch behavior including the mandatory ledger deletion of terminal rows; a keyset-only refetch of `polymarket.markets` **fails** the test (it must run both sweeps); reconciliation deviation blocks publish via check 9.

## Dependencies and parallelization

- **Task 1 blocks everything** — Task 2 cannot build constituents without it.
- Tasks 2 → 3 → 4 are strictly sequential (build, then contract, then gate).
- Tasks 6 and 7 are independent of 2–4 and can run in parallel with *them*; 7 depends on 1 only for the fingerprint bump.
- **Tasks 6 and 7 are NOT independent of each other — do not dispatch them as two unrelated parallel workstreams.** Task 6's refresh set consumes Task 7's early-invalidated tombstone ids, and Task 7's trigger 2 consumes Task 6's refresh set. The coupling is resolvable but must be resolved *first*: agree the two signatures in Task 6's "Shared interface with Task 7" bullet and the three-phase order in Task 7a's "Trigger ordering" **before** either implementation starts, and have whichever task lands first commit both signatures as typed stubs. Built blind and in parallel, these two tasks produce either a circular import or two incompatible notions of what the refresh set contains.
- Task 7 also writes into Task 4's `checks.py` (the reconciliation gate). If 7 lands after 4, that gate is the wiring step; if before, 4 must not re-implement it. See Task 4 hard check 9.
- Task 9 (site) depends on Task 3's golden fixtures and nothing else — it can be built in parallel with 5–8.
- Tasks 5, 8, 10 are sequential after 4.
- Task 11 is last and requires human sign-off.
